# 📘 Chapter 35 — Testing JavaScript

JavaScript-এর **Testing** হলো এমন একটি process যার মাধ্যমে আমরা যাচাই করি আমাদের code **ঠিকভাবে কাজ করছে কি না**, কোনো bug আছে কি না, এবং নতুন feature যোগ করার পর পুরোনো functionality নষ্ট হয়েছে কি না।

Full Stack Developer হিসেবে Testing জানা খুব গুরুত্বপূর্ণ—বিশেষ করে **React, Node.js, API এবং production application** বানানোর সময়।

---

# 35.1 — Testing কী?

**Testing** হলো code-এর expected behavior এবং actual behavior compare করে দেখা।

সহজভাবে:

> “আমি যে output আশা করছি, আমার program কি সত্যিই সেই output দিচ্ছে?”

### Real-Life Example

ধরো তুমি একটা calculator বানিয়েছ।

তুমি আশা করছ:

```text
2 + 3 = 5
```

Testing করে আমরা যাচাই করব:

```javascript
add(2, 3) === 5;
```

যদি `5` আসে → Test Pass ✅
অন্য কিছু আসে → Test Fail ❌

---

# 35.2 — কেন Testing দরকার?

ধরো তোমার একটি বড় e-commerce website আছে।

এখানে:

```text
Login
 ↓
Product Search
 ↓
Add to Cart
 ↓
Checkout
 ↓
Payment
 ↓
Order Confirmation
```

তুমি Login feature পরিবর্তন করলে ভুল করে Cart-এর code নষ্ট হয়ে যেতে পারে।

Testing থাকলে automatically ধরা যেতে পারে:

```text
Login Test        ✅
Search Test       ✅
Cart Test         ❌
Payment Test      ✅
```

তখন developer বুঝতে পারবে কোথায় সমস্যা হয়েছে।

# 35.4 — Manual Testing vs Automated Testing

## Manual Testing

Developer/User নিজে application ব্যবহার করে পরীক্ষা করে।

উদাহরণ:

```text
Open website
↓
Enter email
↓
Enter password
↓
Click Login
↓
Check result
```

### সুবিধা

- সহজ
- UI/UX যাচাই করা যায়
- Human behavior বোঝা যায়

### অসুবিধা

- সময় বেশি লাগে
- বারবার করতে হয়
- Human error হতে পারে

---

# 35.5 — Automated Testing

Code নিজেই অন্য code-এর behavior পরীক্ষা করে।

উদাহরণ:

```javascript
expect(add(2, 3)).toBe(5);
```

এখানে মানুষকে manually calculator চালাতে হচ্ছে না।

Test framework automatically check করবে।

```text
Testing
```

# 35.7 — Unit Testing

**Unit Test** হলো application-এর সবচেয়ে ছোট testable অংশ পরীক্ষা করা।

যেমন:

```javascript
function add(a, b) {
  return a + b;
}
```

এখন আমরা শুধু `add()` function-টি test করব।

```text
Input → add() → Output
```

### Example

```javascript
function add(a, b) {
  return a + b;
}
```

Test:

```javascript
expect(add(2, 3)).toBe(5);
```

এখানে পুরো application test করা হচ্ছে না।

শুধু:

```text
add()
```

test করা হচ্ছে।

### Real-Life Example

একটি restaurant-এর kitchen-এ:

```text
Rice cooking → আলাদা test
Chicken cooking → আলাদা test
Sauce → আলাদা test
```

প্রতিটি ছোট অংশ আলাদাভাবে ঠিক আছে কিনা পরীক্ষা করা = Unit Testing-এর মতো।

---

# 35.8 — Integration Testing

Integration Testing-এ একাধিক component/module একসাথে কাজ করছে কিনা test করা হয়।

উদাহরণ:

```text
Login Function
      ↓
Authentication Service
      ↓
Database
```

শুধু Login function নয়।

পুরো interaction test করা হচ্ছে।

### Example

```javascript
loginUser()
    ↓
API
    ↓
Database
    ↓
User Response
```

এগুলো একসাথে ঠিকভাবে কাজ করছে কিনা পরীক্ষা করা হবে।

---

# 35.9 — Unit vs Integration

| Unit Testing     | Integration Testing      |
| ---------------- | ------------------------ |
| ছোট অংশ test     | একাধিক অংশ test          |
| সাধারণত isolated | Components interact করে  |
| দ্রুত            | তুলনামূলক ধীর            |
| Function test    | API + DB ইত্যাদি test    |
| সহজ debugging    | Debugging তুলনামূলক কঠিন |

# 35.12 — Regression Testing

তুমি নতুন feature যোগ করলে:

```text

     ↓

     ↓
```

নতুন change-এর কারণে পুরোনো functionality নষ্ট হয়েছে কিনা check করা হলো **Regression Testing**।

# 35.13 — Test Case কী?

একটি নির্দিষ্ট behavior পরীক্ষা করার জন্য যে condition এবং expected result তৈরি করা হয় সেটিই Test Case।

উদাহরণ:

### Login Test Case

```text
Test:
Valid email + valid password

Expected:
Login successful
```

আরেকটি:

```text
Test:
Valid email + wrong password

Expected:
Error message
```

---

# 35.14 — Test Scenario vs Test Case

### Test Scenario

High-level requirement।

```text
Test Login functionality
```

### Test Case

Specific condition।

```text
Valid email + valid password
Valid email + invalid password
Empty email
Empty password
Invalid email format
```

# 35.15 — Assertion কী?

Testing-এর সবচেয়ে গুরুত্বপূর্ণ concept-এর একটি হলো **Assertion**।

Assertion হলো:

> “আমি যে result আশা করছি, actual result কি সেটার সাথে match করছে?”

উদাহরণ:

```javascript
expect(2 + 3).toBe(5);
```

এখানে:

```text
Expected → 5
Actual   → 5
```

তাই:

```text
PASS ✅
```

যদি:

```javascript
expect(2 + 3).toBe(6);
```

তাহলে:

```text
Expected → 6
Actual   → 5

FAIL ❌
```

# 35.20 — `expect()` কী?

# 35.22 — `toEqual()`



# 35.31 — `beforeEach()`

প্রতিটি test-এর আগে চলে।

```javascript
beforeEach(() => {
  console.log("Before test");
});
```

Example:

```javascript
beforeEach(() => {
  console.log("Preparing...");
});

test("Test 1", () => {
  expect(1 + 1).toBe(2);
});

test("Test 2", () => {
  expect(2 + 2).toBe(4);
});
```

Output conceptually:

```text
Preparing...
✓ Test 1

Preparing...
✓ Test 2
```

---

# 35.32 — `afterEach()`

প্রতিটি test-এর পরে চলে।

# 35.38 — Mocking কী?

# 35.44 — Coverage-এর ধরন

সাধারণভাবে coverage metrics:

```text
Statements
Branches
Functions
Lines
```

### Statements

কতগুলো statement execute হয়েছে।

### Branches

`if/else`, ternary ইত্যাদির কতগুলো path test হয়েছে।

### Functions

কতগুলো function test হয়েছে।

### Lines

কতগুলো code line execute হয়েছে।

# 35.50 — Testing Pyramid

Testing strategy বোঝার জন্য খুব গুরুত্বপূর্ণ concept:

```text
           /\
          /  \
         / E2E\
        /------\
       /Integration\
      /--------------\
     /  Unit Tests    \
    /------------------\
```

সাধারণ ধারণা:

```text
Many Unit Tests
       ↓
Some Integration Tests
       ↓
Fewer E2E Tests
```

কারণ Unit test সাধারণত দ্রুত এবং focused।

E2E test তুলনামূলক বেশি setup/সময় নিতে পারে।

---

# 35.51 — TDD কী?

**TDD = Test-Driven Development**

এখানে আগে test লেখা হয়, তারপর implementation।

Process:

```text
Write Test
    ↓
Test Fails ❌
    ↓
Write Code
    ↓
Test Passes ✅
    ↓
Refactor
```

এটাকে প্রায়ই বলা হয়:

```text
Red → Green → Refactor
```

---

# 35.52 — TDD Example

প্রথমে test:

```javascript
test("add should return 5", () => {
  expect(add(2, 3)).toBe(5);
});
```

এখন `add()` নেই।

তাই:

```text
FAIL ❌
```

তারপর code:

```javascript
function add(a, b) {
  return a + b;
}
```

এখন:

```text
PASS ✅
```

তারপর code clean/refactor করা যায়।

---

# 35.53 — BDD কী?

**BDD = Behavior-Driven Development**

এখানে application-এর behavior-এর ওপর বেশি focus করা হয়।

উদাহরণ:

```text
Given user is logged out
When user enters valid credentials
Then dashboard should appear
```

এটি human-readable behavior description-এর মতো।

---

# 35.54 — Test Doubles

Testing-এর সময় real dependency-এর পরিবর্তে বিভিন্ন ধরনের substitute ব্যবহার করা হয়।

Common types:

```text
Dummy
Stub
Mock
Spy
Fake
```

### Dummy

শুধু parameter পূরণ করার জন্য।

### Stub

নির্দিষ্ট response দেয়।

### Mock

Interaction verify করতে সাহায্য করে।

### Spy

কোন function কীভাবে call হয়েছে observe করে।

### Fake

Simplified working implementation।

---

# 35.55 — Spy Example

ধরো:

```javascript
const user = {
  login() {
    return true;
  },
};
```

Spy দিয়ে check করা যায়:

```text
login()
কতবার call হলো?
কী argument গেল?
```

Jest-এ সাধারণভাবে:

```javascript
const spy = jest.spyOn(user, "login");

user.login();

expect(spy).toHaveBeenCalled();
```

# 35.56 — Snapshot Testing

Snapshot Testing UI/component-এর rendered output-এর snapshot save করে রাখে।

পরবর্তীতে output পরিবর্তিত হলে test সেটা detect করতে পারে।

Concept:

```text
Current UI
   ↓
Snapshot
   ↓
Future UI
   ↓
Compare
```

তবে snapshot blindly accept করা উচিত নয়।

কারণ snapshot বড় হয়ে গেলে meaningful review কঠিন হতে পারে।

---

# 35.57 — Negative Testing

শুধু valid input test করলে হবে না।

Invalid input-ও test করতে হবে।

ধরো:

```javascript
function divide(a, b) {
  if (b === 0) {
    throw new Error("Cannot divide by zero");
  }

  return a / b;
}
```

Test:

```javascript
test("division by zero throws error", () => {
  expect(() => divide(10, 0)).toThrow("Cannot divide by zero");
});
```

# 35.62 — Test Independence

একটি test অন্য test-এর ওপর depend করা উচিত নয়।

খারাপ:

```text
Test 1 → creates user
Test 2 → assumes user exists
```

Test 1 fail করলে Test 2-ও fail করতে পারে।

ভালো:

```text
Test 1 → own setup
Test 2 → own setup
```

---

# 35.63 — Flaky Test

যে test কখনো pass করে, কখনো fail করে—তাকে **Flaky Test** বলা হয়।

উদাহরণ:

```text
Run 1 → PASS
Run 2 → PASS
Run 3 → FAIL
Run 4 → PASS
```

সম্ভাব্য কারণ:

- Timing issue
- Race condition
- Network dependency
- Shared state
- Random data
- External service

Flaky test dangerous কারণ developer test result-এর ওপর trust হারাতে পারে।

# 35.67 — Testing vs Debugging

দুটো একই নয়।

| Testing                 | Debugging                    |
| ----------------------- | ---------------------------- |
| Bug আছে কিনা খোঁজে      | Bug-এর কারণ খোঁজে            |
| Expected vs actual      | Problem কোথায়                |
| Test automated হতে পারে | Developer investigation করে  |
| আগে থেকেই করা যায়       | সাধারণত failure-এর পর করা হয় |

উদাহরণ:

```text
Test → Login failed ❌
           ↓
Debugging
           ↓
Wrong password comparison
           ↓
Fix
```

# 35.72 — একটি Complete Mini Project

### `calculator.js`

```javascript
function add(a, b) {
  return a + b;
}

function subtract(a, b) {
  return a - b;
}

function multiply(a, b) {
  return a * b;
}

function divide(a, b) {
  if (b === 0) {
    throw new Error("Cannot divide by zero");
  }

  return a / b;
}

module.exports = {
  add,
  subtract,
  multiply,
  divide,
};
```

### `calculator.test.js`

```javascript
const { add, subtract, multiply, divide } = require("./calculator");

describe("Calculator", () => {
  test("adds two numbers", () => {
    expect(add(2, 3)).toBe(5);
  });

  test("subtracts two numbers", () => {
    expect(subtract(5, 3)).toBe(2);
  });

  test("multiplies two numbers", () => {
    expect(multiply(4, 3)).toBe(12);
  });

  test("divides two numbers", () => {
    expect(divide(10, 2)).toBe(5);
  });

  test("throws error when dividing by zero", () => {
    expect(() => divide(10, 0)).toThrow("Cannot divide by zero");
  });
});
```

Run:

```bash
npm test
```
